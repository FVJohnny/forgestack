## J. Backend reliability

- [x] **128. A poison Kafka message wedges its partition forever** (Medium)
  The inbox has bounded retries and dead-lettering, but only for events it has accepted. Failures before acceptance rethrow from `eachMessage` (`backend/libs/kafka/src/kafka.integration-event-listener.ts:88-100,125-146`): unparseable JSON, the deliberate "message has no id" throw, or a Mongo outage during `insertIfNew`. The rethrow prevents the offset commit, so kafkajs redelivers the same message indefinitely with no backoff, counter, or DLQ, blocking that partition and everything behind it. Transient DB errors deserve the retry; permanently malformed messages need a skip-and-log or dead-letter path. Classification: broken/must fix. Fix: distinguish permanent parse/id failures (skip + log/DLQ, commit the offset) from transient ones (retry).
  **Status: Done.** Added a `PoisonMessageError` thrown by `parseMessage` for the two unrecoverable cases (unparseable JSON, no id to dedupe on). `eachMessage` now catches it specifically, logs loudly, and returns WITHOUT rethrowing, so the offset commits and the poison message is skipped instead of blocking its partition forever. All other errors (transient) still rethrow to prevent the commit and be retried once the dependency recovers. A real DLQ topic is the natural next step, noted in the code. Updated the parseMessage spec to assert `PoisonMessageError` for the no-id case and added an unparseable-JSON case.

- [x] **129. Mongo inbox `reclaimStuckEvents` is non-atomic and can resurrect a completed event to PENDING** (Medium)
  `inbox.mongodb-repository.ts:100-121` does `find(PROCESSING)` then a per-doc unconditional `save()`. Between the find and the save, the instance that owns the claim can finish and write PROCESSED; the reclaim then overwrites it back to PENDING (retryCount+1) and the handlers run again. The outbox got this right with a single conditional `updateMany` filtered on the PROCESSING marker; the inbox reclaim should be the same one-shot conditional update. Second problem: it ages events by `receivedAt`, which never advances, so a retried or late-claimed event more than the stuck threshold past receipt is treated as stuck even while genuinely in flight, burning a retry and letting a second instance run the same handlers concurrently. Classification: broken/must fix. Fix: conditional update on status, and add a claimed-at timestamp to age by (mirroring the outbox's claim-time bump).
  **Status: Done.** The Mongo inbox claim now stamps `updatedAt` at claim time (the atomic `findOneAndUpdate` sets it alongside `status: PROCESSING`), and `reclaimStuckEvents` ages by `updatedAt` instead of `receivedAt`, so a retried or backlogged event that is legitimately in flight is no longer insta-reclaimed. The reclaim is now race-safe: after computing the reclaimed state via `reclaimFromProcessing()` (which keeps the branching PENDING-vs-FAILED domain logic), it applies the change with a guarded `updateOne` filtered on `status: PROCESSING`, so an event the owner completed between the find and the write is not overwritten back to PENDING. Chose the guarded-update approach over a single `updateMany` because the requeue-vs-dead-letter decision is branching domain logic. Added a Mongo spec (3 cases against real Mongo): a genuinely-stuck event is reclaimed, a recently-claimed one is not, and a completed-after-read event is not resurrected. The in-memory repo is single-threaded (no race) so it is left aging by receivedAt. All 65 mongodb tests pass.

- [x] **130. Kafka publisher keys messages by unique event id, so per-aggregate ordering is not preserved** (Medium)
  `kafka.integration-event-publisher.ts:16-33` sets the Kafka message key to `parsed.id`, the event's own unique id. Two events about the same aggregate (`user.created` then `email.verified` for one user) therefore hash to different partitions and can be consumed out of order, discarding the per-topic ordering the outbox loop carefully preserves at publish time (item 30). The comment also claims the key "ensures deduplication," which Kafka does not do outside log compaction. Classification: would improve. Fix: key on the aggregate/entity id, or document that ordering is per-event only and drop the dedup claim.
  **Status: Done.** Added an optional `aggregateId` to `Base_IntegrationEventProps` (serialized in `toJSON` when set) and keyed the publisher on `aggregateId ?? id`, with a comment stating the ordering guarantee (per-aggregate when set, none on the id fallback) and correcting the false "deduplication" claim. Set `aggregateId: props.userId` on the five user-scoped example events so the template demonstrates per-user ordering. Added a publisher spec (keys by aggregateId, falls back to id, undefined on unparseable payloads).

- [x] **131. `Base_MongoRepository` caches a rejected index-init promise forever and goes stale when a collection is dropped** (Medium)
  `base.mongo-repository.ts:38-55,165-223` memoizes index initialization in a static map keyed by collection name. If init fails once (Mongo briefly unreachable at boot, exactly when repositories are constructed), the rejected promise is cached permanently and every later operation on that collection rethrows even after Mongo recovers, until process restart. Item 60 made the failure loud; caching the rejection makes it permanent. Separately, the lock is never invalidated, so `MongodbTestService.cleanup()` dropping a collection leaves the lock saying "initialized" while the unique `id` index is gone, which `insertIfNew`'s E11000-based dedup (item 33) silently depends on. Classification: would improve (with a broken corner). Fix: evict a failed init from the map so it retries, and invalidate on collection drop.
  **Status: Done.** Lock creation moved into `getOrCreateIndexLock()`, used by both the constructor's eager kick-off and `ensureIndexes()`. A rejected attempt evicts itself from the static map (with an identity check so a newer attempt is never evicted), so the next operation retries instead of rethrowing the cached rejection until restart. Added `Base_MongoRepository.invalidateIndexLock(collectionName)` and `MongodbTestService.cleanup()` now calls it in a `finally` after dropping the collection. New 3-case spec against real Mongo: a failed init is retried on the next `ensureIndexes()`, a successful init is shared across instances (no re-run), and the unique `ux_aggregate_id` index is recreated after a drop. All 68 mongodb tests and the full 8-project suite pass.

- [x] **132. Redis integration-event listener fabricates message ids (the item 45 bug, unfixed on the Redis side)** (Medium)

  **Status: Done.** `parseMessage` now mirrors the Kafka listener: it uses the payload `id` (the only stable source; Redis pub/sub has no message key) and throws instead of fabricating a timestamp id; the phantom `messageId`/`eventId` reads are gone. Added a 3-case parseMessage spec mirroring the Kafka one. Full suite (8 projects) and typecheck pass.

Fix: only run the retry/dead-letter path when the publish itself threw.
