- [x] **178. Default Mongo `socketTimeoutMS` of 5s aborts any operation longer than 5 seconds** (Low)
  `getMongoConfig()` sets `socketTimeoutMS: Number(process.env.MONGO_SOCKET_TIMEOUT_MS) || 5000` (`backend/libs/mongodb/src/mongodb-config.service.ts:49`). `socketTimeoutMS` is a per-operation socket-inactivity timeout, so any single query, aggregation, `deleteMany` cleanup, or index build that takes longer than 5s is killed with a socket error. The template ships batch cleanup paths (`deleteProcessed` over inbox/outbox collections) and eager index creation that can exceed 5s on a loaded or cold database. It is env-overridable, but the driver default is unlimited, so this out-of-the-box default is an aggressive footgun that causes intermittent, hard-to-diagnose failures under load. `connectTimeoutMS` and `serverSelectionTimeoutMS` at 5s are reasonable; the socket-level 5s is the outlier. Classification: improve. Fix: raise the default (for example 30000-60000, or leave it unset) while keeping `serverSelectionTimeoutMS`/`connectTimeoutMS` at 5s, and document the trade-off in the env template.
  **Status: Done.** Raised the default `socketTimeoutMS` from 5000 to 45000 (still env-overridable via `MONGO_SOCKET_TIMEOUT_MS`), keeping `serverSelectionTimeoutMS`/`connectTimeoutMS` at 5s for fast connectivity fail. Added a code comment explaining the distinction. Added a unit spec asserting the default and the env override. Documented the trade-off in the code comment rather than the env templates: none of the Mongo tuning vars (max pool, selection timeout) appear in the env examples, so adding just this one would be inconsistent; they are all optional overrides with sane defaults.

## T. Security

- [ ] **189. Production frontend CSP still allows `http://localhost:*` and a blanket `https:` in `connect-src`** (Low)
  Item 152 gated only `'unsafe-eval'` behind `isDev`, but `connect-src` is built unconditionally as `"connect-src 'self' https: http://localhost:* http://127.0.0.1:*"` and ships identically in production (`frontend/public-page/next.config.mjs:50`). Two weaknesses remain in the prod bundle: `https:` lets an XSS payload exfiltrate to any HTTPS host, defeating CSP's exfiltration-mitigation purpose, and `http://localhost:*`/`http://127.0.0.1:*` are dev-only API fallbacks with no reason to be in a production policy. The same file (line 46) already demonstrates the `isDev` gating pattern. Classification: improve. Fix: build `connect-src` conditionally: in production restrict it to `'self'` plus the explicit API origins (the `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_SERVICE2_API_URL` hosts), and only append `https:`/`http://localhost:*`/`http://127.0.0.1:*` when `isDev`.

- [ ] **190. JWT verification does not pin the signing algorithm** (Low)
  `JwtModule.registerAsync` sets only `secret` (`backend/libs/common/src/auth/jwt-auth.module.ts:16-20`), and both `JwtAuthGuard.canActivate` (`jwt-auth.guard.ts:50`) and `JwtTokenService.verifyAccessToken/verifyRefreshToken` (`jwt-token.service.ts:42-52`) verify without an `algorithms` allowlist. With the current HS256 symmetric secret this is safe (jsonwebtoken ties the accepted algorithm to the key type and rejects `none` and asymmetric tokens), so this is purely latent: a forker who later switches to an RS/ES key pair, or adds a `publicKey`, inherits a classic algorithm-confusion / key-substitution risk with no signal that pinning was required. For a production-ready template this is a cheap defense-in-depth default. Classification: improve. Fix: pin `algorithms: ['HS256']` in the JwtModule `signOptions`/`verifyOptions` and pass `{ algorithms: ['HS256'] }` to every `verify`/`verifyAsync` call.
